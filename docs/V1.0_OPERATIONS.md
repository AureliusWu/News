## 数据与代码分离

候选 workflow 先从最后成功发布的 Pages 恢复 event-registry 与最近数据代，再采集并校验；第一次兼容升级从 legacy 明确 bootstrap，后续缺失/损坏状态失败关闭，不能默默改变 ID。保留最近三代数据及有界90天事件状态，不以 Actions cache 作唯一持久存储。

scheduled run 可以从公开 release.json/app-bundle.zip 校验并恢复兼容代码，然后 overlay 新数据，避免每次数据刷新重建 UI。没有兼容代码归档的旧生产首次仍完整构建；代码推送仍完整测试/构建。代码摘要还原已有本地证据，但公开恢复与调度复用没有生产证据。

GitHub 的计划任务可能延迟甚至被丢弃，cron 不是服务时效承诺，参见 [官方故障排查文档](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows)。保留原定两小时目标，不能拿 job 成功率替代数据新鲜度。

2. 新闻或报告延迟：看 generated_at/代号；跨代文件拒用，失败保留已读缓存，不改时间或用空数据伪装成功。

4. 存储失败：提示及时导出，本次内存阅读继续；不宣称持久化成功。
5. 注册表损坏：停止发布，恢复最后经过校验的配对数据；不重置事件 ID。
