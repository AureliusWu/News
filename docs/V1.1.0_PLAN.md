# News V1.1.0 更新方案

日期：2026-10-25，Asia/Shanghai。

状态：2026-10-25 用户已通过“按你说的更新”授权实施，按 M0 -> M4 顺序推进。执行证据见 [V1.1_EXECUTION.md](V1.1_EXECUTION.md)。本文不是正式发布记录。

候选身份约定：冻结后应用版本为 `1.1.0`，显式 `CANDIDATE`、`formal_release=false`，界面标注候选，GitHub 预发布标签为 `v1.1.0-rc.1`。真实观察绑定该版本与完整源码 SHA；通过后由同一源码构建正式元数据和状态标签，避免仅因最后改版本号而借用其他版本观测。影响采集、缓存、契约或业务的源码变更仍须重新冻结。正式标签 `v1.1.0` 在门禁完成前不创建。

## 1. 版本定位

建议下一正式版本为 **V1.1.0：稳定更新与持续阅读**。

核心结果：新闻更新状况可判断，手机打开更快，收藏与升级可靠，读者可以持续跟进一个事件，并保存常用筛选条件。

采用一个版本、顺序交付的方式：可靠性 -> 性能 -> 持续阅读功能 -> 兼容与发布收束。仅在发现需要立即上线的生产缺陷时单独发布 V1.0.1；它不是默认新增的必经版本。新增功能受阻时先削减功能范围，不降低数据正确性和收藏安全要求。

## 4. 执行阶段

### M0：冻结基线与收拢现状，约 1 个工作日

1. 读取实际代码与最新运行证据，冻结本轮任务清单、候选身份、数据契约、浏览器支持范围和性能测量条件。
2. 汇总已有 V1.0.0 真实观测，计算截至执行时的窗口、缺测、失败和更新间隔。去重采用 UTC 时刻，原始副本及失败记录保留。过期、缺失的 Actions 产物记为缺失，不补造历史。
3. 将 `ARCHITECTURE.md`、`V1.0_OPERATIONS.md`、旧计划及 `AGENTS.md` 中的当前入口指向已发布交接与新计划；保留历史段落并标明日期，清除“仍等待用户手工标 200 对”等失效待办。
4. 固定 V1.0.0 的代码、数据、浏览器存储与回滚包作为比较基线。未完成门禁登记为历史遗留，核实后才能关闭。

出口：基线清单和任务表完整；每项具有负责人角色、验收方法、证据位置及状态。代理负责代码、自动回归和证据整理；真实设备与外部账户仅在自动化无法提供时需要用户协助。

### M1：更新可靠性与可恢复发布，约 2 至 3 个工作日

1. 沿用独立于采集任务的公网读取，分别记录快照生成时间、观测时间、最新原文发布时间与部署完成时间。采集器、发布、数据年龄和来源覆盖分别判断。
2. 检查失败重试、超时、并发互斥、上次有效代次恢复，以及观测历史的保留方式。重试次数有界；重复触发不产生交叉代次发布。
3. 验证失败时保留原有效数据，新闻、事件和来源健康报告的代号及摘要一致；损坏状态必须显式报错，禁止重置稳定事件 ID。
4. 在现有来源报告与状态提示中区分正常、延迟、缓存和不可用；来源超时、无近期条目、HTTP 错误分别呈现。重复失败提示去重，避免持续打扰。
5. 补齐从 GitHub Release 归档恢复的入口，校验 SHA-256、代码与数据配对以及归档路径，解决 Actions 产物到期后的恢复缺口。先隔离恢复验证，再进行发布阶段演练。

出口：正常刷新、采集失败、损坏文件、重复任务、报告跨代与归档恢复均有实际证据；只在采集与发布平台本身能支持的范围内声明可靠性。

GitHub 官方明确说明计划任务可能延迟，负载高时可能丢弃任务。新增同平台 cron 不能称为独立保障。保留现有免费路线；独立外部观测或触发服务作为可选适配项，接入前确认免费额度、凭据与维护责任，不能预先承诺两小时 SLA。[GitHub schedule 文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

### M2：移动端首屏与交互，约 2 至 3 个工作日

1. 先用真实请求与渲染轨迹定位网络、JSON 解析、脚本执行和列表渲染成本；保持已有快照预热、共享请求与非阻塞缓存写入。
2. 优先减少首屏工作量与不必要渲染，延后非首屏组件。只有测量证明完整快照是主要瓶颈时，才增加轻量索引及按需数据加载。
3. 若拆分数据，采用增量兼容契约，保留旧客户端需要的 `news.json`；索引、分页、事件与来源报告绑定同一代次，异常时提供可验证的回退路径。
4. 在相同冻结新闻、浏览器版本、设备和网络配置下，交替运行 V1.0.0 与候选；保存全部原始样本，桌面与移动配置分别核验。
5. 补实测交互：筛选、搜索、收藏、进入事件详情和恢复页面。首屏快不能替代交互快，受控实验不能替代公网与真机证据。

出口：桌面和移动各至少 5 次冷启动有效对照；报告中位数、最差值与每次原值，目标全部有效样本 LCP <=3000 ms。新增交互目标为固定设备和数据规模下操作到稳定界面 p95 <=200 ms，每类至少 20 次有效操作，独立报告，不称为真实用户 INP。

### M3：事件关注与筛选方案，约 2 至 3 个工作日

1. 在现有事件页加入关注/取消关注；阅读库提供关注事件入口和新增报道数，避免在首页再堆一套信息流。
2. 用稳定文章 ID 比较已见集合，按原有去重规则计算新增报道。旧文章重排、快照裁剪和标题变化不能被计为新报道；事件别名迁移保留关注。
3. 当前快照没有某个事件时显示“当前快照暂无报道”，保留关注。清除关注必须来自明确用户操作，不能因数据过期自动删除。
4. 基于现有 URL 筛选增加命名方案，支持恢复、编辑、删除；保存实际筛选值，不保存翻译后的显示名称。失效来源提示并允许修改。
5. 复用现有本地状态与导入导出，确定有界存储上限和迁移版本；导入先验证再写入，非法文件不覆盖现有收藏，写入失败不伪称持久化成功。

出口：关注、别名迁移、增量去重、快照裁剪、筛选恢复、刷新持久化和导入导出均通过针对性回归；320/390/768 px 布局可用，键盘可完成核心操作。浏览器模拟尺寸不计作真机验收。

### M4：兼容、候选观察与正式发布，约 2 个工作日加真实观察期

1. 运行后端、采集、恢复、前端、发布元数据测试，类型检查及 snapshot/API 两模式构建。保留后端和采集器的独立 Python 环境。
2. Chrome、Edge、Firefox 覆盖在线阅读核心；真实 Service Worker 离线、刷新和更新分浏览器记录支持情况。升级至少覆盖 V1.0.0 及已知旧 0.9 客户端，收藏、已读、设置和新增状态均使用非空样本。
3. 真机目标为 Android Chrome 与 iPhone Safari；已安装 PWA 记录单独的安装、更新和离线结果。没有设备记录就标为未执行，不再以模糊确认替代型号、浏览器、步骤和结果。
4. 复现并定位历史内置浏览器事件点击未导航现象；保留 Chrome/Firefox 与内置浏览器的区别。原有深链接保持兼容，HTTP 404 与 SPA 实际渲染分别报告。仅在有界静态入口方案通过容量和旧链接回归后修复状态码，不默认迁移托管平台或改写全部 URL。
5. 修正发布状态生成逻辑：候选、门禁通过、明确豁免分开表达；版本、源码、数据契约和证据相互绑定。V1.0.0 的一次性批准不能自动授权 V1.1.0。
6. 冻结候选后启动真实七天观测。自动回归、性能、公网检查和观测结果齐备后决定发布，归档原代码与原数据，完成实际发布及发布后检查。

出口：完成 `V1.1.0_HANDOFF.md`、验收矩阵及发布说明，记录源码、标签、CI、部署、数据代次、升级与回滚证据；任何豁免另列版本绑定记录。

## 5. 验收口径

| 项目 | 目标与判定 |
| --- | --- |
| 七天新鲜度 | 保留原门槛：真实跨度 >=168 小时，336 个闭合半小时窗口，有效且快照年龄 <=2 小时的窗口 >=95%，即至少 320 个；失败和缺测保留在分母 |
| 观测身份 | 绑定明确版本、源码和数据契约；同窗口重复记录不能重复计分。V1.0.0 历史只能证明旧版本，不借作新版本通过证据 |
| 候选冻结 | M0 明确候选到正式版的身份规则；单纯版本字符串不能覆盖源码差异。影响采集、缓存、时效或契约的变更发生后，重新建立候选观测期 |
| 数据一致性 | 新闻、事件、来源报告同代；错误/损坏数据不能替换有效发布；旧数据不能更改生成时间伪装新数据 |
| 首屏性能 | 桌面/移动配置可审计，固定数据下各至少 5 次冷启动对照，LCP <=3000 ms；公网样本单独报告，不将实验室结果直接称为生产 SLA |
| 核心交互 | 每类 >=20 次，固定条件下 p95 <=200 ms；样本、失败及设备条件完整保留 |
| 状态安全 | 非空旧数据升级后保留；导出/导入往返一致；非法输入、配额不足、存储拒绝及离线有明确结果 |
| 新增功能 | 关注与筛选方案恢复正确；跨代、别名、裁剪与重复文章不造成新增报道误计或收藏丢失 |
| 浏览器与真机 | 自动化、桌面实测、视口模拟、真机和已安装 PWA 分栏；跳过与未运行不是通过 |
| 回滚 | 归档可校验并恢复原 app+data，恢复原时间；不得用重新采集代替原快照恢复 |
| 发布绑定 | 测试对象、应用源码、发布标签、线上元数据可对应；文档后续提交与应用发布提交明确区分 |

现有脚本的统计与发布规则应在 M0 核实并冻结；实现阶段不得为了得到绿色结果选择样本、改变窗口分母、降低预算或把工作流成功当成业务达标。

## 6. 五类旧豁免如何处理

| V1.0.0 历史豁免 | V1.1.0 处理 |
| --- | --- |
| 七天覆盖及独立调度不足 | 汇总最新旧版证据，再建立新版候选窗口；免费平台限制持续记录，不能以补 cron 宣布解决 |
| 移动性能不达标、交互未测 | M2 修复并补实际对照；历史失败保留 |
| 缺真实手机结果 | M4 独立设备矩阵；缺设备时可继续其他工作，最终状态明确 |
| 历史客户端 / PWA / 跨浏览器矩阵不足 | 先覆盖明确支持的 V1.0.0 和 0.9 路径，其余逐项列出，不宣称全历史兼容 |
| Windows 原生启停与故障注入未执行 | 保留为原生路径独立遗留；公开 Pages 版本不宣称包含原生运行时全量认证，也不绕过执行环境限制 |

正常发布目标是完成约定门禁。若仍存在外部能力缺口，输出影响范围、证据与可选缩减方案；进入新版本豁免发布需要该版本的明确决定，不能直接复制旧批准。数据错配、收藏丢失和无法恢复有效版本属于本计划必须修复的问题。

## 7. 实施落点与依赖顺序

以下是实现阶段的定位入口，具体文件在阶段开始时按实际代码确认；本轮未修改这些业务模块。

| 工作流 | 主要落点 |
| --- | --- |
| 更新与观测 | `.github/workflows/deploy-gh-pages.yml`、`observe-news.yml`，`scripts/observe-public.mjs` 与既有快照/门禁工具 |
| 归档恢复 | `.github/workflows/restore-pages.yml`、`scripts/restore-pages-artifact.py`、配对恢复测试 |
| 性能 | `frontend/src/bootstrap.ts`、`startup/warmup.ts`、`snapshot/transport.ts`、现有首页/列表与 `scripts/browser/performance.mjs` |
| 关注与筛选 | 现有 EventsView、LibraryView、阅读状态持久化与 URL 筛选模块 |
| 升级与发布 | 现有 PWA 更新流程、`scripts/browser/`、`scripts/write-release.mjs`、`scripts/release-approval.mjs` 与元数据测试 |
| 文档 | 当前架构、运维、路线图、新版验收矩阵与最终交接 |

顺序为 M0 -> M1 -> M2 -> M3 -> M4。每阶段实现后先做相关回归，阶段出口通过再推进；冻结候选后尽量只做观测、文档与不改变候选的验证，避免不断重启七天窗口。

预计实现及自动回归约 9 至 12 个工作日，候选冻结后另需至少 7 个自然日真实观察。设备与外部依赖可能延长日历时间；上述为工作量估计，不是固定发布日期。已有旧版本九天的日历跨度不自动满足新候选要求。

## 8. 本版边界与后续方向

- 延续免费 Pages/Actions 快照发布，不要求 Docker、常开个人电脑或公网数据库。Cloudflare 继续保持用户此前的暂缓决定。
- 本版不引入账户、跨设备云同步、推送通知或个性化推荐服务；关注与筛选先在本机浏览器内提供。
- AI 内容生成、翻译和多源综合保持关闭及零预算；事件算法不做大规模重写。已有 AI 评估明确标记来源，不转写成人工审核。
- 优先复用已安装组件。若确需新依赖，实施前说明收益、体积、License 和维护成本。
- V1.2 可在 V1.1 稳定后单独规划可选翻译、事件质量迭代或跨设备同步，届时再决定服务和费用方案。

初始规划轮仅新增本方案并更新路线图入口。用户随后已授权实施；当前代码、验证、同步和部署状态以 [执行记录](V1.1_EXECUTION.md) 为准。
