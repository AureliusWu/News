# V1 M5 缓存等待优化与性能复测（2026-10-15）

快照传输层已完成缓存等待优化并发布，前端 127 项测试、类型检查及两种构建模式通过。移动模拟仍存在 **3.192 秒**的 LCP 样本，三秒性能门禁继续未通过，V1.0.0 尚未正式发布。

## 已发布的代码变更

源码修订：`5e55cf7d5a5014bc4c55b7f9aad18bbede966380`。

[发布运行 38697977138](https://github.com/AureliusWu/News/actions/runs/38697977138) 于 `2026-10-15T07:21:06Z` 标记成功，构建和部署均完成。应用保持 `0.9.0-alpha.1 / M5-candidate`，`formal_release=false`。

此前 `frontend/src/snapshot/transport.ts` 在发起网络请求前等待 `CacheStorage.open`，并在返回已验证的新闻前等待 `Cache.put`。慢缓存可能使在线内容等待本地存储。

本轮变更让缓存打开与网络请求并行，在线新闻验证通过后立即返回，持久化在后台执行。每个传输实例仅有一个缓存写入器，保留最新的一个待写入快照，避免旧写入覆盖新快照以及待写入队列无限累积。网络失败时仍使用已验证的内存或持久缓存，并继续标记缓存回退状态；校验规则、时间限制、游标代际绑定和缓存命名均未调整。

新增四项故障控制测试覆盖：

1. 缓存打开未完成时，在线请求仍能返回新闻。
2. 缓存写入延迟时，在线显示不等待；写入完成后，新传输实例可从缓存离线回退。
3. 缓存配额失败后，在线内容及已有内存回退仍可用。
4. 首次写入阻塞期间的多次刷新只保留最新待写入快照，最终离线读取不会回退到较旧的写入。

这些测试证明缓存等待已从在线返回路径移除，尚不能证明全部线上渲染尾延迟均由缓存引起。

## 性能方法与可比范围

使用已缓存的 Lighthouse `13.5.0` CLI 与本机 Chrome `155`，公开 URL 为 <https://aureliuswu.github.io/News/>。每组依次执行三次桌面、三次移动模拟导航，采用冷配置文件、默认存储重置、`throttlingMethod=simulate` 和性能分类审计。

桌面配置为 1350×940、40ms RTT、10240Kbps、CPU 系数 1；移动模拟为 412×823、设备像素比 1.75、150ms RTT、1638.4Kbps、CPU 系数 4。两组控制参数均与原配置相符，具体值和浏览器环境保存在机器回执中。参见 [Lighthouse 官方配置说明](https://github.com/GoogleChrome/lighthouse/blob/main/docs/configuration.md)。

本轮先测量变更前的 `c03f23e1d9c9c2c86b1c368d49af283d3a4e0e43`，再测量已发布的 `5e55cf7d5a5014bc4c55b7f9aad18bbede966380`。两组各自的前后 HTTP 探针确认应用修订和新闻响应内容在组内不变；发布同时重新采集了新闻，前后组快照不同，因此不能把结果差异全部归因于代码变更。

2026-10-11 的旧测量使用 Chrome 154，本轮使用 Chrome 155。历史桌面 4.36 秒样本仍保留，不将跨浏览器版本的变化解释为已证明的优化收益。
